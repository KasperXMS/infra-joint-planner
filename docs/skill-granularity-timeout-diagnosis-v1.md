# Skill Granularity Pilot v1：180 秒超时诊断

这是正式 30-cell 结束后的只读诊断。没有新增模型调用、补跑、修改服务或改写原始结果。

**直接触发因素是本地 Manager 固定 180 秒 HTTP 超时；三路 cell 流水共用单槽 Orin GPU 推理服务，排队与实际处理都在这个等待窗口内。** 提高 cell 并发时没有同步处理单槽排队与请求超时的关系，导致执行配置影响了 TSR。忽略 E2E 指标并不能消除这种影响：等待一旦触发超时，就变成未完成结果。

## 客户端证据

原执行代码 `scripts/lightweight_planner_pilot_v1.py` 的 local HTTP client 和 OpenAI client 均明确设置 `timeout=180`，SDK `max_retries=0`。任务总预算另为 3,600 秒；这些是单请求超时，不是任务总预算耗尽。

11 个失败均来自本地 Manager，4B 四次、9B 七次、27B 零次。计量 receipt 的耗时范围为 **180.002716–180.004942 秒**，HTTP status、response body、usage 均未取得。每次只有一个已记录 HTTP 调用，未自动重试。所有 11 个请求的 context preflight 都为 `allow`，输入范围 5,982–26,403 tokens，加预留输出 2,048 均在 32,768 窗口内。因此不能把这 11 次解释成 context-limit 拒绝；9B t1 S2 的真实 context-budget 拒绝是另一个独立结果。

## 服务端证据

A28 Planner 后端使用 CUDA Orin，模型 33/33 层 offload 到 GPU，线程数 8、batch 线程数 8、context 32,768、推理槽数 1。这不是模型意外落到纯 CPU 的证据。cell 并发上限 3 并未把服务请求并行度改为 3；多 cell 的 Manager 请求会竞争同一个槽。此机制与 [Ollama 并发说明](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)一致。

保留的服务日志出现 11 条约三分钟结束的 `/v1/chat/completions` HTTP 500，与 11 条取消任务记录及客户端超时对应。这种 500 出现在客户端退出的取消路径，不能直接当作 Qwen XML/JSON parser 返回了错误答案，也不能说是云 API 不稳定。原有云 Verifier 成功响应最大耗时：4B 组 5.806 秒，9B 组 6.789 秒，27B 组 4.173 秒。

一个明确排队案例是 **9B t1 S0**：客户端请求在 10:40:30 UTC（香港 18:40:30）开始；前两个槽内任务的已报告时间分别约 84.256 和 70.913 秒，响应在 10:41:54、10:43:05 UTC 附近完成。第三个请求直到前序任务释放槽后才得到处理，约 10:43:30 被取消；该请求只记录约 21.58 秒未完成 prefill。这个案例说明固定 180 秒的大部分窗口被前序工作占用，不能把整段等待当作该请求自己的推理耗时。

**9B t1 S3** 还有一组取消时的统计：已完成 prefill 47.269 秒、已运行 decode 27.814 秒，共 75.083 秒；模型调用计量为 180.315 秒，两者差额约 105.232 秒包含排队及请求侧开销。这里的 75.083 秒是取消前已消耗的推理时间，不是自然完成所需时间；剩余生成时间未知。这进一步确认了不能把 180 秒全部归到单请求计算，但也不能据此保证取消排队就一定在 180 秒内完成。

槽内详细日志并非每行都有 wall-clock 时间戳，也没有跨所有层统一的 request ID。逐请求准确的 queue/prefill/decode 分解仍有证据限制；不能声称每个超时都只由排队造成，或串行执行必然能完成所有这些请求。Orin 的实际处理耗时、上下文长度及缓存切换同样可能贡献。4090 上的 27B 部署与 Orin 的 4B/9B 也不是纯容量对照。

## 对结果的影响与后续配置方向

30 个原始结果保持不变。11 个超时应作为共享部署下的服务等待失败记录；本轮 9B TSR 0/3 不能等同于“9B 没有能力答对这些任务”。此前细粒度 Skills 没有提升观测 TSR 的结论仍是数据事实，但独立的能力和最优粒度解释受到这项配置影响。

若另行开展复评，应在新协议中把服务 admission/排队与单请求执行时限分开，给实际 Orin 处理设置合适且有上限的 read timeout，或在显存与硬件允许时使用真正的多槽服务/独立实例。仍需保留任务总预算和 STOP；不能直接把超时关闭，也不能假设多槽一定更快。应统一新的匹配条件，不能只选择本轮失败 cells 补跑。本次诊断没有执行这些变更或启动新实验。
