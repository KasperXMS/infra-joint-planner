# Infra-aware logical adapter decision

The decision threshold is empirical, not architectural: a live, original
benchmark task must admit at least two *different logical* workflows that
both satisfy the task-quality constraint, have measured and interpretable
cost differences across infrastructure conditions, and offer enough potential
benefit to pay for extra control work. Historical Stage 2 did not meet that
threshold: Blind 3/12, Raw Aware 2/12 and Cost Ledger 1/12 TSR, despite
21/24 L2 structural differences. This package keeps the Stage 3 48-cell
No-Go in force.

The fixed-workflow comparison is an opportunity measurement. It does not
test whether the open-ended Manager can propose both alternatives, or whether
an infra-aware selector chooses well. The eight-case Verifier protocol test
reduces one engineering failure mode but is not evidence of logical
adaptation. The offline bounded-lookahead tests prove a legal state-transition
interface; they do not show a real pending suffix or a live quality-safe
PATCH opportunity.

**Decision: No-Go for developing a full Infra-aware Logical Workflow Adapter
from this evidence.** The [controlled result](../../results/infra-workflow-opportunity-v1/controlled-public.json)
does establish two distinct, executable logical workflows with four valid
original-task successes on the same real Video-MME question. The contact-sheet
path adds local image composition, reduces model input from 7,512 to 1,943
reported tokens and reduces action transfer by 777,341 bytes. Yet it wins by
measured E2E in *both* network states: 157.554 s fast and 3.464 s slow.
There is no observed preference reversal for an infrastructure-conditioned
selector to exploit. The dramatic cross-state change in model service time
for byte-identical evidence and prompts further confounds any bandwidth-only
causal interpretation. No cost crossover is manufactured by adjusting
weights or dropping the common source-staging cost.

The next narrow research step is to find another real, quality-acceptable
logical pair with an actual communication/compute trade-off and to control
resident-model cache state, preferably with a different original task or
counterbalanced preregistration. The current registry cannot send the raw
MP4 to a video-capable resident model, so the historically suggested
"centralized raw" strategy is not a valid third condition here. If a future
pair shows a quality-matched infrastructure-dependent preference after
serving-state control, a *separate* small live feasibility test should ask
whether the SDK-native Manager can naturally propose a dependency-valid
pending fragment. Only then would an adapter that weighs profile intervals,
quality risk and its own control overhead have a concrete method target.
This package does not start that next study or the old Stage 3 matrix.
