# Harness v2 implementation report

The four ordered milestones were committed separately: execution correctness `877d6de`, workflow state `8001a8e`, SDK/native formal integration `25646a9`, and recovery/interface/reporting in the final milestone commit.

Execution correctness changes are in `control/gateway.py`, `control/physical.py`, `runtime/action_receipts.py`, `runtime/client.py`, `runtime/executor.py`, `worker/server.py`, both benchmark runners, and the Worker CLI. The gateway now persists per-action states and settles successful siblings even if another child raises. Controller and Worker receipt digests bind an ID to a request. A second request with a different payload is rejected. Remote completion after a lost reply can be reconciled from the Worker; recovered service work remains unknown rather than invented. The ledger wrappers retain confirmed partial outcomes. The Worker receipt ID is scoped by the physical batch UUID to avoid collisions between runs that reuse logical action names.

Terminal and Specialist changes are in `control/verification.py`, `control/native_agents.py`, and `control/contracts.py`. The Verifier chooses a candidate action ID; the Harness derives and validates the exact output hash and graph version. Legacy unbound complete records remain parseable but cannot complete a new run. Specialist failures now reach the Manager as typed JSON and are stored as typed `SubagentResult`, with no fabricated action ID. `failure_error_function=None` prevents the SDK from silently converting nested-agent exceptions into a success-looking text answer.

Workflow state changes are in `control/workflow.py`, `control/workflow_validation.py`, `control/workflow_state.py`, and `control/native_workflow_bridge.py`. Open fragments are validated without pretending a terminal exists. Sealing applies the existing full-plan validator. Formal PATCH reuses `apply_workflow_patch()` and changes only pending actions at a quiescent frontier. The opt-in native bridge routes actual SDK tool actions through the formal plan and the unchanged action gateway. Its deterministic scripted test covers fragment, seal, PATCH, and execution. No infrastructure-conditioned PATCH selector was implemented.

Recovery and future interfaces are in `control/recovery.py`, `control/feasibility_interface.py`, and `control/verifier_offline.py`. The feasibility module defines only resource-blind query/assessment/provider types. The verifier module analyzes existing traces offline; live Verifier frequency remains unchanged. No benchmark, evaluator, frozen Skill, historical result, semantic Manager prompt, Physical Scheduler policy, or AutoDL service was changed.

Tradeoffs: the bridge is opt-in, so unchanged historical runs retain their original execution semantics. An SDK Manager that never declares a complete dependency-connected terminal plan retains an open plan; the harness does not invent semantic edges. The first recovery policy is fail-closed no-resume, not a distributed checkpoint framework. File receipts are durable for a single process per directory and do not guarantee exactly-once effects across a Worker crash between external side effect and receipt write.
