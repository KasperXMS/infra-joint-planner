# Why H2 did not expose a pending frontier

The frozen [H2 observation](../harness-v2-baseline-requalification/harness-v2-formal-bridge-feasibility.md) comprises two real cells, separate from Stage 2 H1: MultiHop proposed six actions, LongBench one; both had zero declared dependencies, zero pending actions at the end, no seal, and no KEEP/PATCH frontier. MultiHop exhausted Manager turns; LongBench hit a Verifier raw-schema failure. Neither was selectively rerun.

**Source-confirmed behavior.** `NativeFormalWorkflowBridge.prepare` in `src/infra_joint/control/native_workflow_bridge.py:34-58` accepts one SDK tool proposal, validates it, appends a one-action fragment, then immediately reserves and starts that action. The current Manager tool surface therefore exposes only a present action, without a separate proposal of future actions, explicit multi-action dependencies or a seal decision. The formal state machine itself is more capable: `VersionedPendingWorkflow.append_fragment` in `workflow_state.py:168-221` accepts multiple actions and dependencies, `keep_or_patch` at `workflow_state.py:303-350` operates on a sealed quiescent frontier and checks rewrite provenance. The H2 result primarily tests the *bridge interface*, not whether the validator can maintain pending state. The single-action LongBench path cannot tell whether the Planner would have planned ahead if offered such an interface. The MultiHop path shows that repeated immediate dispatch does not spontaneously create a suffix.

The opt-in scripted `BoundedLookahead` prototype in `src/infra_joint/control/bounded_lookahead.py` offers `propose(1–3 actions, dependencies, expected_version, optional terminal_action_id)` followed by explicit `ready_action_ids`, `dispatch_ready`, `settle` and `keep_or_patch`. It reuses the existing `OpenSemanticWorkflowPlan`, `SemanticWorkflowPlan` and `VersionedPendingWorkflow`; it never invents a semantic action or picks a patch. A Planner can submit one action when uncertainty is high, or two/three when it can name valid future dependencies. A proposed fragment is validated **before** the ready action dispatches. Completed and running actions remain locked; sealed pending actions can be patched only at a quiescent frontier with known provenance. If no pending suffix exists, no adaptation opportunity is claimed or forced.

**Reproduced interface tests.** Deterministic scripted tests cover a two-action retrieval→answer fragment and artifact edge, seal, dependency-gated dispatch, status settlement, KEEP, PATCH of the pending answer with completed retrieval preserved, rejection during running execution, rejection of unknown provenance, open-plan KEEP rejection, and the one-to-three-action bound. Existing formal-state tests additionally cover incremental fragments and stale versions. This validates the state transition shape, **not** a live SDK-native Manager's ability to generate useful fragments, cost-aware patch selection, physical execution, or task-quality improvement. No full Infra-aware Adapter was built; live feasibility and the value of a pending frontier remain open.
