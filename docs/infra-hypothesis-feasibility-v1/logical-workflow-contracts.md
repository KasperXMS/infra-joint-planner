Frozen after P1 Go and before any new LLM task execution. If source/evaluator validity fails, replace with the next D2 row of the same family in parent manifest order, documenting the technical reason. Wrong answers never trigger replacement.

Both workflows use the same original question, original short-text answer contract, independently held native evaluator, source inventory and final reasoning model/prompt. The Controller runs only inside the P1 mount-isolated environment. No private answer, supporting-document annotation or gold relevance ID enters `/study`, a Worker, retrieval, prompt or model request. Source operation IDs, hashes, input/output representations, network bytes, latency and missing evidence are logged.

| Step | G0: centralized evidence processing | G1: source-side information reduction |
|---|---|---|
| MultiHop acquisition | Use question-explicit source names (`TechCrunch`, `Hacker News`) to select all original articles in those publisher groups from the public source manifest. Read each through its owning Worker's receipted `read_artifact` operator. Central Controller performs deterministic lexical ranking of these original records. This is per-query acquisition; there is no free central cache. | Each source Worker runs the existing `bm25_retrieve` over its full resident corpus shard using the unmodified question, returning its top four complete records as a versioned retrieved-passage-set artifact. | MultiModalQA acquisition | Read all ten original text candidates and the one original table candidate through their owning Workers, using the original task's public context references. Controller selects relevant text from the full candidate set. | Before trials, build a source-local derived JSON candidate index from the same ten original text artifact IDs; record all source hashes and the one-time build cost. Source-a runs existing `bm25_retrieve` over that index (top three) and sends the reduced records. Source-b transfers the same original table artifact as G0. |
| Final synthesis | The frozen final model receives the original question and selected evidence with original IDs/provenance. | The same final model and task-level prompt receives locally selected evidence with original IDs/provenance. |

The semantic distinction is **when and by which information dependency evidence is selected**: G0 acquires full query-scoped originals before central filtering; G1 irreversibly selects records at each source before transfer. They differ in evidence acquisition, retention and potential loss, not merely operator placement. For MultiHop, G0's question-explicit publisher scope and G1's whole-shard BM25 are themselves different acquisition policies. We will separately report that scope difference, so no cost effect is attributed solely to placement. For MMQA, both have exactly the same ten text and one table candidate scope; only source-side reduction differs. No G2 is preregistered because no validated local semantic extraction capability has been established.

Both workflows may fail quality. A G1 retrieval miss, G0 central ranking miss, model error, context overflow, malformed answer or Worker failure is an outcome. A pair qualifies for H1 only if both independently meet native task success and the information-flow difference above is observed in traces. Reduction never implies semantic equivalence or quality preservation. Setup includes the MMQA derived index and any serving model load; resident execution excludes those one-time costs but reports them separately.
