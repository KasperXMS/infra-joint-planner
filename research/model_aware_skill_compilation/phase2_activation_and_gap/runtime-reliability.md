# Runtime reliability diagnosis

The fixed WP1 comparison retains the preceding pilot's 16,384-token context, Codex auto-compaction threshold 14,000, tool permissions and 900-second task budget. No runtime change is silently applied to S1/S2/S3. An unchanged copy of the prior [16-cell diagnostic register](evidence/prior-pilot-diagnostics.md) and [score summary](evidence/prior-pilot-summary.json) is starting evidence; the new [activation register](evidence/activation-summary.json) is analyzed separately.

Four old-pilot cells had HTTP 400 **model context rejections**: 9B `weighted-gdp-calculation-4` S1, 9B `financial-analysis-3` S0, and both 27B spreadsheet S1 cells. Their official reward remains 0, but none is a clean completed-task observation. The first 9B rejected request exceeded the configured 16,384-token maximum by at least one token. Codex's 14,000-token compaction threshold left limited headroom for a long next tool observation or prompt prefix; compaction did not guarantee that every subsequent request fit. The prior pilot's largest successful response usage was 16,123 input tokens. These facts establish a runtime boundary, not the precise cause of each Agent decision.

The spreadsheet family magnified the issue. Under 9B S2, the exact original `xlsx` body appeared in all 137 and 98 model requests, yet the two Agents logged 42 and 46 multiple-compaction warnings, repeated 47 and 38 command occurrences, timed out, and left their workbooks unchanged. Native S0/S1 spreadsheet traces also had many tool-router errors: 64 and 46 in the first instance; 129 in the second S0. Most were model-generated attempts to request elevated permissions under the frozen `never` policy or inconsistent `justification` arguments. They are not SSH transport failures or verifier errors. Codex's fallback metadata warning for the custom Qwen model may also affect context estimates and action behavior; the evidence does not quantify its independent contribution.

Repeated full-context request tokens do not directly equal GPU work or monetary cost because vLLM prefix caching can reuse computation. The pilot retained response usage, client-side first-byte and later-response timing, and five-second GPU power samples; it did **not** obtain isolated server-side prefill/decode measurements or a confirmed cloud rental rate. WP1 reports the same categories and does not treat a shorter prompt as task-quality improvement. The 27B GPTQ-Int4 reference uses both cards and is not a matched throughput comparator for 9B BF16.

In the frozen nine-cell WP1 validation, three official-zero cells had HTTP 400 model context rejection: S1 repetitions 1 and 3, and S3 repetition 1. A fourth S1 cell exhausted its Agent time budget, with 33 compaction warnings, 124 repeated command occurrences and no output artifact. All three S2 cells completed without context rejection or transport failure and produced an artifact; two still failed the same stock-only answer check. The S3 completed cells likewise produced artifacts but did not read a main Skill. In this small sample the shorter S1/S3 prompts did **not** avoid context failure, while the longer S2 prefix did; history growth and behavior matter more than static Skill length alone. Tool-router errors were 2, 2 and 0 in S2 repetitions 1–3, and 0 in S1 and S3 except one error in the earlier S3 development probe. These are separated in the [activation receipt](evidence/activation-summary.json) rather than recoded as infrastructure-invalid runs.

A separate **non-task** serving probe stopped only the study-owned 16K 9B vLLM service, launched the same model and settings with `--max-model-len 32768` on GPU 0, and sent a synthetic long Responses request. The service became healthy and returned HTTP 200 with **18,020 input tokens**, above the frozen 16,384 limit. The probe service was then stopped and the original 16K service relaunched and checked healthy. The [probe receipt](evidence/32k-runtime-probe.json) establishes startup and one long request on the 32 GB GPU; it does **not** establish sustained 32K Agent reliability, successful auto-compaction, tool-call correctness, or a changed task score. Any task experiment at 32K needs a separately frozen runtime condition. No AutoDL instance stop/restart occurred.

The separate loaded-original-Skill offer-letter diagnostic shows another failure mode in task economics: the final DOCX passed the official verifier, but Codex did not terminate before the Agent budget. Its 163 model requests contained the exact original Skill body, and the trace recorded 48 compaction warnings and 48 repeated command occurrences without a context rejection. The final file's retained modification time was early in the run. This is a completion/stop-policy and interaction-efficiency problem, not an official task failure. It reinforces why binary score, agent exit state, tool loops, latency and energy must be reported together.

The court diagnostic was not made clean by a stronger reference model. The 9B S2 run had 40 failed shell calls in 49 and emitted a zero-page PDF, despite normal model transport. The 27B S2 run improved the intermediate artifact to a valid six-page PDF but still had 24 failed shell calls in 75, 21 compaction warnings, and a late HTTP 400 context rejection at 16K. Both had the original main Skill in every request and neither opened its referenced `forms.md`. The 27B official score remained 0. This is a mixed model/tool/context boundary, not evidence of a successful strong-model solution that a procedural compiler might transfer to 9B.

After the conditional 27B reference, the study-owned 27B process and its temporary bridge were stopped; the original 9B BF16 16K service was restored on GPU 0 and returned HTTP 200. GPU 1 was idle in the [final service check](evidence/final-service-state.json). The AutoDL instance itself was never stopped or restarted.
