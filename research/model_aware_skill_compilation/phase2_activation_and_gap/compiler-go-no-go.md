# Compiler decision: No-Go for implementation in this phase

The evidence supports a **narrow, source-linked procedural-failure hypothesis**, but not yet a general Model-aware Procedural Skill Compiler. The strongest signal is the new financial instance: original main Skills were in every S2 request, the source offers a helper that distinguishes total from stock holdings, and two of three S2 trials produced a total-holdings answer to a stock-only question despite successful artifact creation. One S2 trial passed. This gives a concrete rule-selection/completion-check target, not a demonstrated compiler benefit. No compiled condition was run, and the failure was observed on only one new instance from a family already used for development.

| Decision requirement | Evidence and limit |
|---|---|
| Valid source task and unchanged verifier | Financial, offer-letter and court reference oracles all scored 1; the financial negative artifact scored 0. |
| Original Skill correctly delivered | Exact original main bodies reached every S2 request in the scored trials. Referenced resources still require an Agent read; the court 9B Agent did not read `forms.md`. |
| Runtime basically stable at the decision | Financial S2 had no API/transport rejection and all three runs completed, but compaction and some shell/router errors remain. Offer-letter passed only after an Agent timeout; court 9B had 40 failed shell calls and an invalid PDF. Stability is not established across families. |
| Identifiable procedural decision | The financial stock-subtype versus total-count choice is specific and source-traceable. The court outcome is resource/tool-confounded; offer-letter was an official success. |
| More than a visibility problem | Two financial S2 failures remain after exact main-body delivery. This separates that symptom from native discovery failure, while leaving comprehension, tool choice and compaction as possible causes. |
| Source rule can be represented and reused | The original `13f-analyzer` helper/reporting rule is reusable across accessions and instances. Only one new instance has shown this failure under loaded-original conditions. |
| Fair comparison with original loaded Skill | S2 is pinned and reproducible. A future intervention would need the same loading path, task/verifier/tools/budget and a length-matched control; none exists yet. |
| Distinct method beyond prior work | [SkVM and SkillSmith](related-method-boundaries.md) already cover explicit capability-aware Skill transformations and guarded procedural interfaces. A generic rule/checklist IR alone has no defensible novelty claim. |

The immediate research priority is **Skill activation and model/harness capability boundaries**. A 68-token natural-language read trigger did not induce any actual main-Skill read in three new-instance trials or either development probe. S2 gained one official pass, but its 1/3 success and the two repeated stock-count errors show that loading alone is not a reliable solution. Context rejection, compaction and completion-after-artifact loops also need separate controls. The non-task 32K probe only establishes one long-request serving capability, not a repaired Agent runtime.

A later *small, falsifiable* procedural test could encode just the source-supported finance subtype decision: identify the requested holdings subtype, select the helper/report field that corresponds to that subtype, and check the final answer against it before writing. Every clause would carry its original source location; it would contain no accession, expected answer, or held-out instance data. This is a candidate **intervention specification**, not a claimed new compiler. Before coding it, use independent financial instances and a second family with an unconfounded loaded-Skill rule failure; compare the exact loaded original against a length-matched/compact original and against the intervention on fixed tools and runtime. Include SkVM/SkillSmith-style transformations as method baselines if a novelty claim is sought. If the effect disappears after stable runtime or ordinary read gating, the compiler hypothesis should be rejected.

The conditional 27B court reference is reported in the [case studies](procedural-gap-case-studies.md) and [gap receipt](evidence/gap-summary.json). It also scored 0: it made a valid PDF but missed required content, never opened `forms.md`, and eventually suffered a model context rejection. It therefore **does not** establish a strong-model success gap or turn the 9B malformed-PDF trial into a clean loaded-procedure failure.

## Answers to the ten research questions

| Question | Evidence-based answer |
|---|---|
| Q1. Does S3 reliably make 9B read native Skills? | **No.** Both main Skills were advertised, but 0/3 S3 new-instance runs and both previous-development trigger probes opened either main `SKILL.md`. |
| Q2. Does S3 approach S2 on official success? | **No on this one instance:** S3 0/3 versus S2 1/3; S1 0/3. This is not a population estimate. |
| Q3. Is there a context/cost advantage without quality loss? | The S3 treatment is 68 tokens versus 1,202 S2 original-body tokens per request, but S3 lost the only official pass. Cached input totals and five-second GPU energy are not a billing or causal cost saving. |
| Q4. What remains after original Skill delivery? | Two financial S2 runs selected total instead of stock-only holdings; offer-letter kept working long after producing a correct artifact; court 9B failed to enter the referenced form workflow and emitted an invalid PDF. Only the first is a plausible loaded-rule decision failure. |
| Q5. Model capability or runtime/tool boundary? | Financial S2 errors occurred without API rejection but with some compaction/tool failures, so attribution remains mixed. Offer-letter has an extreme continuation/compaction problem despite success. Court has major shell and referenced-resource confounds; 27B also missed that resource and context-rejected, so the pair does not isolate a 9B-specific gap. |
| Q6. Is there a reusable procedural-error family? | **A candidate, not a confirmed general mechanism:** financial analysis reuses the original 13F Skill across instances, and the stock-subtype mistake recurred in two S2 repetitions of the new instance. No clean second-family rule failure has been established. |
| Q7. Is a compilation intervention explicit and testable? | A source-linked subtype-selection and final-check rule can be specified. No compiled condition has been tested, so benefit is unproven and a generic guarded rule overlaps existing work. |
| Q8. Is nearby work already solving similar problems? | **Yes, substantially.** SkVM covers model/harness-aware transformation; SkillSmith covers guarded runtime procedure; SkillReducer covers routing/compression; SkillLens covers consumption-sensitive Skill creation. See the [method review](related-method-boundaries.md). |
| Q9. Is there a credible within-/cross-family protocol? | The pinned one-task 3×3 within-family protocol is auditable but small and partly runtime-confounded. Cross-family evaluation needs new reserved tasks, source-validity gates and an independently frozen runtime; current document cases are development diagnostics. |
| Q10. What should be studied next? | First establish effective Skill activation and stable model/harness/tool boundaries. Then test the narrow source-rule hypothesis against loaded-original and length controls on genuinely unseen cases. A general compiler is premature. |
