# Loaded-original-Skill failure case studies

## Financial analysis, new instance `financial-analysis-4`, 9B S2 repetitions 2 and 3

This is a **candidate rule-selection failure**, not proof that procedural compilation will help. The source [`13f-analyzer/SKILL.md`](https://github.com/cxcscmu/SkillLearnBench/blob/726e1f79b96b0cb3d729d0e55a1c847e0b5353ae/skills/human_authored/financial-analysis/13f-analyzer/SKILL.md) says under “Analyze the holding summary of a particular fund in one quarter” (lines 8–16) to run `one_fund_analysis.py` for an accession and quarter; its output distinguishes total holdings from stock holdings. The task's second question specifically asks how many **stocks** the target fund holds. The same Skill is reusable across the finance instances and did yield a successful S2 run on this instance in repetition 1.

The unchanged original Skill bodies reached **all 44 and all 27 model requests** in repetitions 2 and 3; the full request archive and Agent traces are retained privately. In repetition 2, the Agent found the target fund's accession, then read `SUMMARYPAGE.tsv` and counted all matching `INFOTABLE.tsv` lines. Both observations returned 11 total holdings, which it wrote as `q2_answer=11`. It invoked the Skill's `one_fund_analysis.py` for a *different* fund later in the run, but did not invoke it for the target fund before finalizing q2. In repetition 3, the Agent again examined `SUMMARYPAGE.tsv` and `INFOTABLE.tsv`, did not invoke `one_fund_analysis.py` at all, and gave the same total-holdings answer to the stock-only question. The original verifier passed file existence and the first answer check in both trials, then rejected q2. The public report deliberately omits the hidden expected answer; the private verifier logs and artifacts preserve it. Both official binary rewards are **0**, with Agent exit 0.

The failure is plausibly at **tool/rule selection and completion verification**: a source-supported way to obtain the requested subtype count was available, but the Agent treated an all-holdings count as sufficient. It is not a missing-Knowledge case, because the original body was verified in context. It is also not a model transport failure: neither failed S2 run had an API rejection or transport failure. Repetition 2 logged four compaction warnings, eight failed shell commands and two tool-router errors; repetition 3 logged three compaction warnings, three failed shell commands and no router error. Those facts limit a pure cognitive attribution. The counterexample S2 repetition 1 passed the same official verifier after using referenced scripts, indicating the task is solvable under the fixed model/harness at least once. Two S3 runs made the same q2 mistake without loading the Skill, consistent with the rule being useful but not proof that a compiler is needed to express it.

A future intervention could make the *existing* distinction explicit as a reusable conditional check: when a question asks for a subset such as stock holdings, choose the corresponding helper output rather than the total-row count, and verify the requested subtype before writing the answer. The rule must trace to the cited source body and remain independent of any particular accession or task answer. This idea overlaps SkVM's explicit capability-aware transforms and SkillSmith's guarded boundary contracts; it is not yet a distinct compiler algorithm. A matched loaded-original control and at least one unseen instance/family would be required before claiming improvement.

## Offer letter, new family `offer-letter-generator-2`, 9B S2

The original [DOCX Skill](https://github.com/cxcscmu/SkillLearnBench/blob/726e1f79b96b0cb3d729d0e55a1c847e0b5353ae/skills/human_authored/offer-letter-generator/docx/SKILL.md) body reached all **163** model requests. Its source instructions cover split-run placeholders (lines 10–76) and conditional section markers (around line 176); the final DOCX passed every unchanged official verifier check, including placeholder, nested-table, header/footer and conditional-section checks. The official reward is therefore **1**, even though the Agent continued until its time budget expired (exit 124). The final artifact's retained file modification time was about 114 seconds after trial setup, while the trial lasted about 862 seconds. That timestamp suggests substantial work continued after the artifact was created; it does not independently establish when every verifier condition first became true.

The trace has 69 shell calls, 48 repeated command occurrences, 48 compaction warnings, one tool-router error, no failed shell commands, no API context rejection and no transport failure. This is a **post-artifact continuation/stop-decision and runtime-efficiency case**, not a binary task failure or evidence that the source's DOCX rule needs compilation. The original Skill was loaded, and the result shows at least one document family can be solved under S2 despite severe interaction overhead. A 27B reference on this instance is unnecessary for the present procedural-failure question.

## Court PDF, new family `court-form-filling-2`, 9B S2

The source reference passed the original verifier, but the 9B Agent scored **0**. The unchanged [PDF Skill](https://github.com/cxcscmu/SkillLearnBench/blob/726e1f79b96b0cb3d729d0e55a1c847e0b5353ae/skills/human_authored/court-form-filling/pdf/SKILL.md) body reached all 55 model requests. Line 11 directs form-fillers to [the original `forms.md`](https://github.com/cxcscmu/SkillLearnBench/blob/726e1f79b96b0cb3d729d0e55a1c847e0b5353ae/skills/human_authored/court-form-filling/pdf/forms.md), whose opening rule says to check whether the PDF has fillable fields before choosing a filling path. The Agent made no tool call to open `forms.md` and did not invoke the source's fillability or filling helper scripts. Instead it attempted its own PDF operations; 40 of 49 shell calls failed. The final `/root/sc100-filled.pdf` was 311 bytes and had zero PDF pages, so the verifier could not extract any text and reported 15 errors after other preliminary checks. The Agent exited normally, with four compaction warnings, one router error, no API context rejection and no transport failure.

The observed failure is **resource activation plus tool execution**, with an invalid artifact. Because the referenced procedural body never reached the model, it does not establish that the 9B model read the actual form-filling branch rule and failed to obey it. The high shell-failure rate is a strong confound.

The predeclared **27B S2 reference** also scored **0**. The same unchanged main PDF body reached all 98 requests, but it did not open `forms.md` either. It made 75 shell calls, 24 of which failed, logged 21 compaction warnings, and eventually received one HTTP 400 model context rejection (Agent exit 1). Unlike the 9B artifact, its output was a valid six-page PDF with extractable text and form fields, but the official required-content checks still failed. This shows a better intermediate artifact under the same source-valid task, **not** a strong-model task success or an upper bound. Since both models missed the referenced procedure and the 27B run was context-rejected, the court pair does not isolate a small-model-specific loaded-procedure gap or support a compiler effect.
