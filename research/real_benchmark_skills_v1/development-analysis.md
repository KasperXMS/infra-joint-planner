# Frozen development analysis: native Skills on official SkillsBench v1.1 tasks

This document covers only the eight prespecified development tasks, each run once for Qwen3.5-4B and Qwen3.5-9B under S0 (No Skills) and S1 (unaltered native Skills): 32 official BenchFlow/OpenHands cells. It was written after all 32 original task evaluators completed and before any held-out cell started. The task split, source hashes, model settings, 1,800/900/600-second task budgets, and the S0/S1 alternation were frozen before outcomes. Official binary task resolution is primary. Fractional verifier reward, detailed subtests, ACP traces, tokens and time diagnose failures; they do not replace binary resolution. The run uses the declared Transformers 5.19.0 BF16 SDPA inference fallback behind the same OpenAI-compatible bridge for both conditions, not a vLLM performance result.

| Qwen3.5-4B | 8 | 0 | 0 | 0 | 0 | 0/8 |
| Qwen3.5-9B | 8 | 0 | 0 | 0 | 0 | 0/8 |

Every development cell has an original scoring record and no framework or verifier error. Several tasks passed some original subtests or produced partial artifacts, but all 16 task/model pairs failed under both conditions. Hence there is no observed native-Skill resolution gain in this development set, and the binary metric has a floor. The mean fractional original reward rose from 0.104125 to 0.149125 for 4B and 0.020875 to 0.112125 for 9B; these are descriptive, heterogeneous subtest outcomes from single greedy trials. They cannot establish a Skill-content effect, particularly where the S1 trace shows no Skill read. The held-out set remains unopened, so neither a held-out treatment estimate nor repeatability claim is available here. No domain, difficulty or model-size effect on binary resolution can be inferred from an all-fail development set.

## Delivery, consumption and failure modes

The initial model request contained the exact official native Skill directory names in all 16 S1 cells; none of the 16 S0 requests showed those names. This validates the planned availability contrast, but a name menu alone does not show that the Agent used the contents. Three S1 cells show successful main-Skill content access: 4B Civ6 read `SKILL.md` and bundled rules, 9B court invoked the official `pdf` Skill five times, and 9B Civ6 invoked `sqlite-map-parser` once. No direct bundled Skill-script launch was found. Thirteen S1 cells have no observed successful main-Skill read or invocation; twelve have terminally complete traces and one terminal trajectory is incomplete, limiting an absence claim for that cell. Automated reference-path candidates include two nonzero-exit attempts and must not be counted as successful reference delivery. The court invocation returned the original main Skill body, but its later `forms.md` lookup used a nonexistent cache path; it delivered a valid but substantively incomplete PDF. Both Civ6 S1 and S0 ultimately lacked the required JSON, despite the S1 Skill invocation.

The failure taxonomy is overlapping rather than exclusive. Missing required artifacts occurred in economics, court and Civ6 cases; artifact structure without correct semantics occurred in Azure BGP, dialogue parsing, crystallography and DAPT. Some cells reached the original Agent timeout while the original verifier still ran successfully. The 9B Civ6 S0 comparator timed out after map/database exploration without `/output/scenario_3.json` (zero of ten top-level checks passed); S1 also lacked the JSON after receiving its Skill body. In 9B court, S0 had no PDF while S1 produced a valid PDF that missed required content; this one-pair partial change is not causal evidence of a Skill benefit. The 9B DAPT S1 passed 5/14 subtests versus S0's 4/14, without observed Skill-content access. Case-level hashes and interpretation limits are in `development-case-notes.md` and `development-9b-case-notes.md`.

Across 32 cells, 202 of 918 terminal calls with reported exits returned nonzero and seven exits were unreported. Those include exploratory checks and compound commands, so the rate is a terminal-exit screen, not a task-failure rate or a count of recoverable tool faults. ACP marked one executable action, 14 `think` calls and six other-kind calls as failed; conflating these categories would overstate executable tool errors. Four cell trajectories are incomplete at termination. An exact-adjacent title-and-output screen found 19 additional repeat actions across seven cells; manual review confirms that 9B Civ6 S1 repeated the same late `Get plots by continent` command four times. The screen is a lower bound and not an automatic verdict on all recovery attempts.

## Work and cost boundary

The 32 completed cells account for 36,257,974 provider prompt-plus-completion tokens, 1,928 reconciled backend generations and three logged API transport errors. A hash-verified private AutoDL generation snapshot (`4eb49c5e61e8b63548e355dab2d535589b878d2c63a74dcc8c848804411d33bd`) agrees exactly with API prompt and completion totals in every completed cell. Provider-token totals by 4B S0/S1 are 9,238,146/8,907,979; by 9B S0/S1 they are 8,753,486/9,358,363. Tool calls by the same groups are 349/376 and 336/361. Costs differ in both directions and no task succeeded, so cost per successful task is undefined in development. At the ¥7.35/hour rate supplied in the brief, summed cell-time rental equivalents are ¥65.29; approximate all-in rental since the recorded study start through the last development cell is ¥83.93. The latter includes setup/idle time and continues accruing while the AutoDL instance remains online. Local hardware, electricity and transfers are unpriced; there is no billed per-token API charge. These are measured and estimated execution costs, not a vLLM throughput claim.

## Method decision before held-out evaluation

Observed access failure, missing artifacts after successful Skill invocation, reference lookup failure, semantic implementation errors and timeout-driven incompletion do not reduce to one validated intervention. The apparent candidates—better routing/discovery, progressive disclosure or compression, executable Skill interfaces, absolute-path/environment repair, and stored workflows—overlap the primary work charted in `related-work-boundaries.md` (SkillLens, SkillReducer, SkillSmith, SkVM and Agent Workflow Memory). We did not obtain finite development validation of a literature-distinct, faithful and fair S2 that improves official task resolution without adding task-specific oracle information or shifting planning decisions into the harness. Therefore **omit S2** in the formal held-out study. This is a methodological gate, not a claim that no improved Skill representation could work. RQ5 and RQ9 will report the unsupported intervention claim explicitly rather than rename an existing method or infer it from fractional scores.
