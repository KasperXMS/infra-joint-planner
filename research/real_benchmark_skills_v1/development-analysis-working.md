# Development analysis working notes (27/32 cells)

This is an **incomplete development-stage draft**, not the frozen analysis or a held-out estimate. It covers 13 matched model–task pairs (eight 4B pairs and five 9B pairs) and one unpaired 9B S1 cell as of the 27th completed original SkillsBench v1.1 cell. The other five development cells and every held-out cell are excluded. Original verifier resolution is the primary outcome; fractional reward, subtests, trajectories, and timing are explanations only. The authoritative cell-by-cell record is under the private WSL jobs directory, with separately hashed local archives. Public case evidence is indexed in `development-case-notes.md` and `development-9b-case-notes.md`.

## Observed outcome and delivery

All 27 completed cells have official binary resolution **fail**: eight 4B S0/S1 pairs, five 9B S0/S1 pairs, and 9B court S1 pending its S0 comparator. This is a development observation with a floor effect, not an estimate for the held-out set or evidence that Skills never help. Some tasks have partial original-verifier credit. For example, 4B crystallography S1 reached 4/11 examples and 9B S1 reached 8/11, while neither passed the full task. Their complete trajectories show no native Skill file read, so this is not evidence that Skill contents caused the partial improvement.

The first-request audit confirms the exact official native Skill names in all 14 S1 model system messages and none in the 13 completed S0 messages. The ACP path/action screen finds a successful native Skill *file* read only in 4B Civ6 S1, where the Agent opened `SKILL.md` and bundled rules but never delivered the required JSON. The new 9B court S1 has five completed native Skill invocations returning the original `pdf` Skill body. It then attempted, but failed, to open the packaged `forms.md` reference at an incorrect cache path and produced a valid PDF with missing required content. The path screen's reference-read candidate for that failed command is not a successful reference read. No direct bundled Skill-script launch is currently detected. These are observations about recorded actions: a menu mention does not prove attention or use, and invocation or file reading does not establish correct application.

The original verifier and sandbox ran normally for these 27 cells. Provisional factors can coexist in one task. Do not label ACP `think` failures as executable tool errors or count an exploratory nonzero shell exit as a final task failure without reviewing the private action span. The exact-adjacent repetition screen last found 13 extra actions in five of the first 26 cells; it is a lower-bound candidate screen, not an automatic count of failed recovery.

## Method gate still open

Skill discovery/consumption is a plausible bottleneck, but a better Skill menu, progressive disclosure, routing, structured procedure, or executable interface overlaps published SkillsBench-adjacent work. `related-work-boundaries.md` records the primary-source boundary for SkillLens, SkillReducer, SkillSmith, SkVM, granularity, SkillCraft, and Agent Workflow Memory. The complete 32-cell development analysis must establish both a specific failure mechanism and a fair, literature-distinct candidate with finite development validation before any S2 is frozen. A relabeled compiler/router or a task-specific oracle-derived shortcut would not meet the brief. If no candidate passes that gate, explicitly omit S2 and run the full 64-cell held-out S0/S1 comparison.

At 32/32, regenerate the complete official result, trace, Skill visibility, repetition, paired, Skill-use, tool-error, backend-reconciliation, and cost reports. Inspect task-level artifacts and failures, write the final `development-analysis.md` and `development-method-decision.json`, and run `freeze_development_analysis.py`. Its receipt must exist before the held-out runner starts. This draft alone is insufficient to open evaluation.
