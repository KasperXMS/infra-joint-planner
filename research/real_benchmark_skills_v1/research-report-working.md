# Small language models and native procedural Skills on real Agent tasks

**Status:** user-terminated before completion of the held-out study. Development completed and was frozen; only 7/64 held-out cells have original verifier scores. See the [termination report](user-abort-report-2026-10-14.md) and [partial official-score export](evaluation-user-abort-results.json). No held-out treatment estimate or final RQ1–RQ9 answer is reported. Official verifier outcomes remain the primary endpoint. Raw prompts, traces, artifacts and credentials are stored privately, outside Git.

## Research question and design

This study asks whether the unmodified native Skills supplied with SkillsBench v1.1 improve the real-task resolution of Qwen3.5-4B or Qwen3.5-9B. S0 exposes no task Skill; S1 uses BenchFlow's native Skill injection with the original files, references and scripts. The contrast changes availability, while retaining the same OpenHands Agent, tool and sandbox contracts, model settings, task input, budget and original verifier within a model. It is not a prompt-only paraphrase of Skill contents. Each cell has one greedy trial; tasks, not tool steps or model calls, are the unit of paired comparison.

The fixed SkillsBench v1.1 source is commit `b63b7b2850226b6aa4fb5929a8c1ac7bc4d9a6af`, with the frozen release manifest and BenchFlow 0.6.3. The [protocol](protocol.md), [task-selection lock](task-selection.lock.json), [model lock](models.lock.json), [frozen run configuration](run-config.frozen.json), and [split-family audit](split-family-audit.md) document exact versions, 24 original task-package digests, selection rationale, nonoverlapping task/Skill families and controls. Eight development tasks have 32 S0/S1 cells. After the development decision was frozen, 16 held-out tasks began their required 64 S0/S1 cells. No S2 is run, following the prespecified [development decision](development-method-decision.json). Original task files and verifiers are not altered.

Both frozen splits cover seven broad benchmark domains, with task and Skill families separated across splits. Development has two Easy, four Medium and two Hard tasks; held-out evaluation has one Easy, eleven Medium and four Hard tasks. These are coverage descriptors from the pre-outcome lock, not a post hoc selection based on small-model scores. Domain or difficulty effects will use the actual paired-task denominators and remain descriptive where a subgroup is small.

The AutoDL instance cannot provide a supported Docker sandbox: it has no usable socket and rejects required namespaces. Original BenchFlow task containers therefore run in an isolated local WSL2 Ubuntu 22.04 Docker daemon, while the existing AutoDL RTX PRO 6000 Blackwell serves the pinned BF16 models through one OpenAI-compatible bridge. Oracle, real-Agent, Skill-loading, API/context and container-isolation checks preceded formal cells. A vLLM provisioning failure led to the declared compatible Transformers 5.19.0/PyTorch 2.8.0 BF16 SDPA fallback, used consistently for S0 and S1; its latency and throughput are **not vLLM measurements**. Context is 32,768, thinking is disabled, generation is greedy, output cap is 4,096, and no undeclared schema-constrained decoding is applied. The original official result is not replaced with a synthetic proxy. Details and an excluded pre-Agent Spring Boot bootstrap attempt are in [the first infrastructure amendment](evaluation-infrastructure-repair.md). The identical launcher correction applied before all valid held-out cells; that excluded attempt had no model request or verifier result. A later [context-budget amendment](evaluation-context-repair.md) preserves an unscored ACP error after two exact-token context rejections and prospectively adjusts OpenHands input budgeting and backend output fitting. Both conditions of each valid task pair use one configuration epoch; the first six scored cells are preserved unchanged.

## Frozen development results

All 32 development cells completed with original task scoring. For both models, S0 resolved 0/8 tasks and S1 resolved 0/8: zero rescues and zero regressions on the binary endpoint. This floor limits inference about treatment magnitude; descriptive fractional original-verifier reward varied across task/model pairs, but is secondary. The [frozen development analysis](development-analysis.md), [machine-readable results](development-results.json) and [paired report](development-paired-analysis.json) contain the full denominators, subtest outcomes and cases. The complete development analysis and private archive checks were frozen before any held-out evaluation started.

Every development S1 first model request contained the official Skill name menu, and no S0 request showed those names. Observed successful main-Skill body access occurred in only three of sixteen S1 cells. The remaining traces show no successful main-Skill read or invocation, with an incomplete terminal trajectory in one of those cells; menu delivery therefore cannot be equated with consumption. The cases with body access still failed their task. A 9B court-form S1 case produced a valid but substantively incomplete PDF after invoking the PDF Skill, while its S0 comparator produced no PDF. Both Civ6 comparators lacked the required JSON despite S1 Skill access. These examples support a diagnostic distinction between availability, access, partial artifact delivery, semantic correctness and official resolution; one trial does not identify a causal mechanism. The [Skill-use report](development-skill-usage.json), [trace-signal report](development-trace-signals.json), [visibility audit](development-skill-visibility.json), and [case notes](development-case-notes.md) provide evidence and caveats.

The failure taxonomy is overlapping: missing required artifacts, partially valid output, incorrect semantics, tool/path grounding failures, repeated exploration, and timeout-driven nontermination all appear. A terminal-exit screen found 202 nonzero exits among 918 terminal calls with reported exits and seven unreported exits; these include exploratory checks and are not equivalent to 202 task failures. An exact-adjacent action screen found 19 additional repeats over seven cells, a lower bound rather than a complete recovery measure. Four terminal ACP trajectories were incomplete. The [tool-error analysis](development-tool-errors.json), [repeat analysis](development-exact-repetition.json), and [measurement rubric](completion-measurement-rubric.md) define those limits.

Development produced 36,257,974 reconciled provider prompt-plus-completion tokens and 1,928 backend generations across the completed cells. Backend and API token counts agree per cell against the private hash-verified snapshot. The summed official-cell runtime is equivalent to approximately ¥65.29 at the supplied ¥7.35/hour rental rate; approximate all-in rental from the recorded study start through the last development cell was ¥83.93. Setup and idle rental accrue separately, and local electricity, hardware depreciation and transfer costs have no measured price. Zero binary passes make rental per successful development task undefined. See the [development cost report](development-costs.json) and [cost-accounting method](cost-accounting.md).

## S2 decision and novelty boundary

The development failures are heterogeneous. Observed access failures, missing outputs after an actual Skill call, wrong paths, semantic errors and timeouts do not yield one finite, fair intervention with development evidence of better original task resolution. Routing/discovery, compression and progressive disclosure, executable interfaces, environment binding and workflow memory overlap established methods in SkillsBench, SkillLens, SkillReducer, SkillSmith, SkVM, SkillCraft, the presentation-granularity study and Agent Workflow Memory; see the [primary-source comparison](related-work-boundaries.md). S2 is therefore omitted rather than relabeling an existing method or using held-out outcomes to design it. This leaves RQ5's proposed-representation comparison unsupported, not negative evidence that no representation can help. The defensible contribution is a reproduction and diagnostic account of small-model native-Skill consumption under the specified real-task harness, subject to the held-out results.

## Held-out analysis to complete

The frozen 16-task held-out set must yield 16 S0 and 16 S1 original-verifier results for each of 4B and 9B. Aggregate success rates, paired rescues/regressions, domain and difficulty breakdowns, model-size treatment differences, original fractional subtests, required-artifact completion, observed Skill access, tool/recovery screens, tokens, wall time and all-in rental will be computed only after all 64 official cells and private archives pass completeness checks. The [pre-outcome artifact contracts](evaluation-completion-contracts.json) distinguish delivered files from semantic validity and official resolution. [Working case notes](evaluation-case-notes-working.md) record individual observations without extrapolating to the held-out treatment effect.

The final discussion must answer RQ1–RQ9 with exact denominators and limitations. One trial per task/model/condition does not establish repeatability, statistical significance or a general model scaling law. A positive result would be a within-sample descriptive effect; a zero result with low observed Skill access would not prove that well-applied Skill content is ineffective. Optional 27B or cross-benchmark transfer is contingent on a credible, analyzable mechanism and cannot replace the mandatory 64-cell evaluation.

## Reproducibility and preservation

Public source, configuration, release/task hashes, original scoring summaries and redacted analyses are committed to independent branch `real-benchmark-skills-v1`. Private per-cell archives carry SHA256 receipts in the local backup and are excluded from Git. Final publication requires verifying all 64 original scores and archives, reconciling AutoDL generation counters with API usage, publishing complete evaluation and cost reports, and checking that all research-owned processes are stopped while the AutoDL instance remains online. Its rental continues at the user-supplied hourly rate after the observation point.
