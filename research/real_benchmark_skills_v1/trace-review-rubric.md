# Development trace review rubric

The official verifier decides task resolution. Trace review explains *how* a cell reached that outcome; it must not change the task score or provide an excuse to rerun a failed answer. Use the frozen task and its original test names, `result.json`, the ACP trajectory, private model request metadata, and output artifacts. Cite run ID, trajectory step indices, verifier test names and SHA256 digests. Keep full prompts, tool output, credentials and generated artifacts private.

For each S1 cell, code the following evidence levels independently:

| Code | Minimum evidence | Limit |
| --- | --- | --- |
| Available | BenchFlow `include_task_skills=true` plus sandbox proof for native directory | Does not show the model noticed the skill |
| Presented | The first model system message contains the exact official native Skill names in `<name>` tags | Shows delivery to the model request, not attention, reading, or use; check with `audit_skill_visibility.py` |
| Discovered | Agent lists/references the native skill path or name in a tool action or thought | Could be a superficial mention |
| Invoked | A completed native `kind=skill` / `invoke_skill` ACP event returns the pinned official Skill body | Stronger than menu delivery; count distinct cells and invocations, and check the returned body against the task package. It does not prove a referenced file was opened or the procedure applied correctly. |
| Read | Tool action opens `SKILL.md` or a bundled reference/script for content | Reading alone does not show correct use |
| Executed | Tool action runs a bundled script or command from the skill | Execution may fail or target the wrong data |
| Applied | Trace and artifact show a specific procedural step used on task data | Requires human review; path regex cannot establish this |
| Helpful/harmful | Matched S0/S1 official outcomes and supporting trajectory differences | One greedy trial cannot establish a general causal mechanism |

Code failure factors only where there is affirmative evidence. Categories may coexist: domain knowledge, skill discovery/consumption, tool argument grounding, action sequencing/state tracking, failed-action recovery, artifact/termination completeness, and sandbox/infrastructure. A clean verifier run with reward below one is a task failure; a missing verifier/failed environment is an infrastructure fault. Report unresolved causes as `undetermined`. Tool calls marked `failed` by ACP are candidate tool errors; review their actual status before treating them as model errors. Repeated actions count only when the same relevant operation is retried without useful new state. Recovery success requires a failed step followed by a corrective action and verifier-relevant progress.

An identical information lookup repeated after the same successful output is a redundant, no-progress operation; it is not a failed tool action. For bundled scripts, a terminal `grep`, `cat`, `find`, or file listing over a `.py` path is inspection, not script execution. `extract_trace_signals.py` screens for direct interpreter or script launches and can miss indirect imports. Check the actual command before coding `executed`.

For `read` evidence, the path screen distinguishes opening a Skill file from listing its directory. It also screens terminal content readers such as `cat`, `sed`, and `grep` when their command names an official Skill path; `ls` and `find` count only as discovery. A `grep` attempt with no returned matches is still a read candidate, not proof that useful content reached the model. Relative paths after `cd`, indirect code imports, and content copied through another file may escape the screen, so the original tool output and subsequent action must be checked manually before coding consumption or application.

`analyze_exact_repetition.py` reports consecutive completed ACP actions with identical titles and text outputs, using only hashes and step indices in its public artifact. This is a lower-bound candidate screen: it misses paraphrased or non-adjacent loops and can include harmless repeated checks. Read the private span before labeling an action redundant or failed.

Use `extract_trace_signals.py` only to locate candidate skill paths and failed tool steps. Its path search can miss indirect use or flag a mention in an edited file; review the original private trajectory before assigning `read`, `executed`, or `applied`. In particular, a native `kind=skill` event can return the main Skill body without opening `/skills/.../SKILL.md` as a separate file action; review `n_skill_invocations` and the returned body separately. In 9B court S1, the path screen marked a `forms.md` read candidate, but the shell returned exit one for a missing cache path. That is an attempted reference read, not successful content delivery. Bare Skill directory names are excluded from read detection because names such as `pdf` and `pymatgen` also occur in ordinary task files and libraries. Separate failed ACP `think` and unclassified `other` calls from failed `execute`/`read`/`edit` actions before calculating an environment tool-error rate. In the early economics S1 trace, eight failed calls are all `think` events, so counting them as eight failed terminal actions would be incorrect. Conversely, ACP can mark a terminal call `completed` even when its output reports a nonzero shell exit; the extractor records the last reported exit code separately. A compound shell command can hide an earlier failure, and a deliberately exploratory probe can exit nonzero without indicating final task failure. Review those steps before assigning a recovery or tool-grounding cause. Keep verifier subtest fractions separate from official task success. Compare task pairs and both model sizes descriptively; lack of a skill-use action in one run is an observation, not a law about the model.
